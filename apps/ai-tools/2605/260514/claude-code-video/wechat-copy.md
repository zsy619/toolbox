## 为什么配置比你想象的重要得多

Claude Code 的默认配置，是为"通用用户"设计的，不是为你设计的。

如果你是做出海 Web 开发的，你的场景有很强的特殊性——多语言、Stripe 支付、UTC 时区、Next.js 技术栈……

这些背景信息如果每次都靠你在对话里手动补充，不仅效率低，而且容易忘，一忘 Claude Code 就开始给你生成"通用版"代码。

**好的配置，是让 Claude Code 在开口之前就已经了解你。**

## 一、CLAUDE.md：最被低估的配置文件

这是整套配置里投入产出比最高的一项。

CLAUDE.md 放在项目根目录，Claude Code 每次启动时会自动读取它，把里面的内容当作项目级的"系统提示词"。

你在这里写的一切，Claude Code 都会默默记住，不需要你每次对话都重复交代。

### 我的 CLAUDE.md 模板（300字以内精简版）

```markdown
# 项目背景

出海 SaaS 产品，技术栈：Next.js + TypeScript + Prisma + PostgreSQL + Tailwind CSS

# 开发规范

- 代码风格：函数式写法，async/await，类型放 types/ 目录
- 出海要求：UTC 时区，金额用整数（分），文案走 i18n
- 数据库：snake_case，软删除用 deleted_at

# 常用命令

npm run dev / npx prisma migrate dev / git push origin main

# 注意事项

Stripe Webhook 签名验证不能跳过，环境变量前缀 NEXT_PUBLIC_
```

### 关键教训

CLAUDE.md 不是越全越好，是越精准越好。

我第一版写了将近 800 字，结果 Claude Code 开始"选择性遗忘"——规则太多，优先级模糊。

精简到 300 字以内后，遵守率明显提升。

## 二、模型选择：日常开发别用 Opus

日常编码任务，Sonnet 比 Opus 更适合。

不是因为 Sonnet 更强，而是因为 Opus 想太多——给它一个明确需求，它会开始考虑各种边界情况、提出你没问的架构问题、给你三个方案让你选。

**我的分配策略：**

- **Sonnet**：日常功能开发、Debug、写测试
- **Opus**：系统架构设计、技术选型讨论
- **Haiku**：快速生成样板代码、写注释、改格式

这样分配之后，月账单下降大约 **40%**，同时产出效率没有下降。

## 三、上下文管理：最容易被忽视的效率杀手

用 Claude Code 久了，一定遇到过这个问题：聊到后面，它开始"记错事"——明明前面说过用 TypeScript，它给你生成 JavaScript。

**这不是 Bug，是上下文窗口满了之后的正常退化。**

### 我的三个策略

**策略一：任务拆小，不要一次塞太多**

更好的做法是拆开：先做注册，验收通过，开新对话做登录，以此类推。每个对话聚焦一个功能点。

**策略二：用"摘要接力"保留关键上下文**

每次对话快到上下文上限时，让 Claude Code 做一个摘要：

> 请用200字以内总结我们这个对话里确定的所有技术决策和已完成的实现细节，我会把这段摘要带到下一个对话继续。

**策略三：敏感配置单独声明**

每次涉及 Stripe、数据库、第三方 API 的对话，在开头加一行主动声明：

> 当前项目使用 Stripe，金额单位为分，所有涉及支付的代码必须做幂等性处理。

## 四、Permission 设置：读写分级

Claude Code 执行某些操作时会询问是否允许，默认配置太保守，会频繁打断节奏。

**我的权限策略：**

**总是允许（不每次询问）：**
- 读取任何文件
- 在项目目录内创建新文件
- 运行 npm run 类的脚本命令
- 运行 git status / git diff / git log

**每次确认（保持询问）：**
- 删除文件
- git commit / git push
- 数据库迁移命令
- 安装新的 npm 包

**总是拒绝：**
- 访问项目目录之外的文件系统
- 发起网络请求

**逻辑：低风险操作自动执行提高效率，高风险操作保留人工确认保证安全。**

## 五、出海项目专项配置

### Stripe 相关
```markdown
# Stripe 规范
- 金额统一用最小货币单位（分）
- 所有 Stripe API 调用必须有错误处理
- Webhook 处理必须先验证签名
- 退款、取消订阅等操作需要记录操作日志
```

### i18n 相关
```markdown
# i18n 规范
- 使用 next-intl，locale 文件放 messages/ 目录
- 新增文案必须同时在 en.json 和 zh.json 里添加
- 日期格式使用 Intl.DateTimeFormat
```

### GDPR 相关
```markdown
# 隐私合规
- 用户数据采集必须有明确法律依据
- 删除账号必须真正删除或匿名化
- 日志里不能出现用户的真实邮箱、姓名、IP
```
