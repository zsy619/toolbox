为什么需要理解镜像分层

Docker 镜像由一些 松耦合的只读镜像层 组成,Docker Daemon 负责堆叠这些镜像层,并将它们管理为一个整体,对外表现出的是一个独立的对象。

docker pull 拉取镜像时,每个 pull complete 行就代表下载了一个 镜像层 ——理解这一点对掌握 Docker 镜像原理至关重要。

镜像层核心定义

每个镜像层由两部分构成:
1) 镜像文件系统 :拥有镜像所有镜像层的数据内容;
2) 镜像 json 文件 :描述镜像相关属性的集合,通过 docker inspect <镜像> 可以查看。
两者具有 相同的 imageID 。

Chapter 01

为什么分层?3 大优势

分层有 3 大核心优势,缺一不可:

优势 说明 价值
1. 不可变性 每个分层 只读 ,对分层的修改都是以 新分层 的形式出现,不会破坏原分层内容 镜像内容可追溯、可复现,符合不可变基础设施理念
2. 节省空间 每个分层 只记录变更内容 (类似 Git diff),所以节省磁盘 同一基础镜像的多应用共用底层,避免重复存储
3. 资源共享 不同镜像间可 复用 相同下层镜像 docker pull 本地已存在的分层不重复拉取,节省带宽和时间
💡

docker pull 在拉取之前会先获取要拉取镜像的所有 imageID,然后 在本地查找这些分层 。如果存在,不再拉取,而是共享本地的分层,节省了空间和网络带宽,提高了拉取效率。

1.1 镜像层与 json 文件

每个镜像层由两部分构成:

  • 镜像文件系统 :拥有镜像所有镜像层的 数据内容
  • 镜像 json 文件 :描述镜像相关属性的 集合 ,通过 docker inspect <镜像> 可以查看

两者具有 相同的 imageID 。

Chapter 02

镜像 FS 构成:基础镜像层 vs 扩展镜像层

Docker 镜像文件系统(FS)由多个 只读的镜像层 组成,每层都有特定的功能。这些只读镜像层根据位置与功能不同可分为两类:

类型 位置 作用 典型生成方式
基础镜像层
Base Image 		所有镜像的 最下层 基础镜像层的文件系统称为 根文件系统 (rootfs),是其他层的基础 FROM centos:7 中的 centos:7 即基础镜像
扩展镜像层 基础镜像层 之上 对基础镜像层功能的 扩展 Dockerfile 中 每条指令 都会生成一个扩展镜像层
🎯

rootfs 是建立在 Linux 中" 看不到的 "引导文件系统 bootfs 之上。bootfs 负责系统引导和启动,rootfs 是用户可见的文件系统,两者职责分离。

Chapter 03

容器层(Union File System)

镜像运行起来就成了容器,而容器也具有文件系统。容器的文件系统在 Docker 镜像最外层之上增加了一个 可读写的容器层 。

Union File System 核心思想

对文件的任何更改 只存在于容器层 ,因此不会影响镜像本身。容器要修改某个文件,会从容器层开始向下一层层地查找,直到找到为止——对文件的操作都会记录在容器层。这就是 Union File System(联合文件系统) 的核心思想:多层叠加,下层只读,顶层可写。

3.1 Copy-on-Write 机制

  • 修改文件 :容器层会在镜像层找到文件并 copy 到容器层,然后再进行修改
  • 删除文件 :也只会将容器层中的文件副本删除(不会真的删除镜像层的文件)
  • 新增文件 :直接在容器层创建,镜像层无感知

可以看出,Docker 容器就是一个 叠加后的文件系统 ,这个容器层称为 Union File System 联合文件系统 。

⚠️

容器删除时, 容器层也一并删除 。这意味着:1) 容器内未持久化的数据全部丢失(这就是为什么需要 数据卷 );2) 镜像本身的扩展层保持完整,可被其他容器复用。

Chapter 04

Linux OS 启动过程(bootfs + rootfs)

微内核架构分为 内核(Server) 和 服务模块(Client) 。Linux 的 bootfs 由两部分组成: bootloader 和 kernel 。

💡

关键结论 :各个容器中的 rootfs 就是 由宿主机的 kernel 驱动的 。这就是为什么 Docker 容器可以共享宿主机内核——不需要为每个容器启动独立的 Linux 内核。

4.1 启动流程

  1. 宿主机加电 → bootloader 加载
  2. bootloader 加载 kernel 到内存
  3. kernel 启动后挂载 rootfs (根文件系统)
  4. kernel 准备就绪,启动系统服务
  5. 后续创建的 容器 直接复用 host 的 kernel,各自挂载自己的 rootfs

镜像摘要 digest

每个镜像都有一个长度为 64 位的 16 禁止字符串 (hex) 作为其 摘要 digest 。

5.2 摘要的本质

摘要(digest)是 镜像内容的 Hash 值 ,即所谓的 Content Hash ,只要镜像内容发生变化,其内容散列值就会改变。默认的 Hash 算法是 sha256 。

5.3 为什么有了 tag 还需要 digest?

区分 相同 : 的 不同 镜像。

⚠️

比如镜像 xxx:2.8 在运行中发现 bug,然后进行了修复,然后使用原标签将其 push 回仓库, 原镜像被覆盖 。但是生产环境中还有运行中未修复的镜像容器。此时 标签无法区分 镜像是修复前还是修复后,这时就只能查看 digest 。

特性 tag digest
可变性 可被覆盖/修改 不可变,内容变化 digest 必变
唯一性 tag 相同可能指向不同镜像 全球唯一标识一个具体镜像
使用场景 日常拉取(人类可读) 精确拉取 / 不可变部署(机器可读)
精确拉取 docker pull xxx:2.8 docker pull xxx@sha256:abc...
Chapter 06

分发散列值(Distribution Hash)

在 push 或 pull 时,都会对镜像进行 压缩 以减少网络带宽。但 压缩会改变镜像内容 ,导致传输后与 digest 不符合。

6.1 解决方案

Docker 为镜像配置了 Distribution Hash(分发散列值) :

  1. 在镜像压缩后 计算 分发散列值
  2. 随镜像一同 发送
  3. 接受方收到后,立即 计算 压缩后镜像的分发散列值
  4. 与携带的分发散列值 对比
  5. 如果相同,则传输没问题
🎯

Distribution Hash 解决了" 压缩传输后与原始 digest 不符 "的验证问题。本质是" 内容不同,验证方式不同 "——原始内容用 content hash 标识,传输内容用 distribution hash 标识。

Chapter 07

多架构镜像(Multi-architecture Image)

Multi-architecture Image 多架构镜像是某个镜像针对 不同操作系统/系统架构 的不同镜像实现。即镜像的 : 是相同的,但是针对的操作系统/系统架构不同(如 linux/amd64、linux/arm64、windows/amd64)。

7.1 多架构镜像原理

无论用户使用的是什么操作系统,通过 docker pull 拉取到的一定是针对该操作系统的镜像,用户无需考虑操作系统问题。Docker Hub 能根据 pull 请求自动选择对应的镜像。

7.2 Manifest 文件

镜像的多架构信息保存在 Manifest 文件 中。拉取镜像时:

  1. pull 命令将 OS 与架构信息一并提交给 Docker Hub
  2. Docker Hub 根据 : 查找 Manifest
  3. 如果 Manifest 不存在,直接查找并返回镜像
  4. 如果存在,会根据 Manifest 中记录的地址找到该镜像的位置

7.3 常见的多架构组合

OS 架构 典型场景
linux amd64 普通 x86 服务器、笔记本
linux arm64 Apple Silicon(M1/M2/M3)、AWS Graviton、树莓派
linux arm/v7 老款 ARM 设备、IoT
linux ppc64le IBM Power 架构服务器
linux s390x IBM Z 大型机
windows amd64 Windows Server 2019+ 容器
💡

查看当前 docker 是否支持多架构拉取: docker buildx ls 列出可用 builder。生产推荐启用 docker-container builder,通过 docker buildx build --platform linux/amd64,linux/arm64 . 一次构建多架构镜像。

FAQ

常见问题

Docker 为什么要把镜像分层?

分层有 3 大优势:1) 每个分层 只读 ,对分层的修改都是以新分层形式出现,不会破坏原分层内容;2) 每个分层 只记录变更内容 ,所以节省空间;3) 不同镜像间 实现资源共享 ,即不同镜像对相同下层镜像的复用。docker pull 在拉取之前会先获取要拉取镜像的所有 imageID,然后在本地查找这些分层。如果存在,不再拉取,而是共享本地的分层,节省了空间和网络带宽,提高了拉取效率。

基础镜像层和扩展镜像层的区别?

所有镜像的 最下层 都有一个看得到的基础镜像层(Base Image),基础镜像层的文件系统称为 根文件系统 (rootfs),rootfs 是建立在 Linux 中'看不到的'引导文件系统(bootfs)之上。在基础镜像层之上的镜像层称为 扩展镜像层 ,是对基础镜像层功能的扩展。在 Dockerfile 中,每条指令都会生成一个扩展镜像层。

什么是容器层(Union File System)?

镜像运行起来就成了容器,而容器也具有文件系统。容器的文件系统在 Docker 镜像最外层之上增加了一个 可读写 的容器层。对文件的任何更改 只存在于容器层 ,因此不会影响镜像本身。容器要修改某个文件,会从容器层开始向下一层层地查找,直到找到为止(类似 Copy-on-Write)。这就是 Union File System(联合文件系统) 的本质:多层叠加,下层只读,顶层可写。

镜像摘要(digest) 是什么?

每个镜像都有一个长度为 64 位的 16 禁止字符串 (hex) 作为其摘要 digest。摘要是镜像内容的 Hash 值,即所谓的 Content Hash,只要镜像内容发生变化,其内容散列值就会改变。默认的 Hash 算法是 sha256 。查看方式: docker inspect <镜像> 或 docker images <镜像> --digest 。

为什么有了 tag 还需要 digest?

区分 相同 repository:tag 的 不同 镜像。比如镜像 xxx:2.8 修复 bug 后用原标签 push 回仓库,原镜像被覆盖。但生产环境还有运行中未修复的镜像容器,此时 标签无法区分 镜像是修复前还是修复后,这时就只能查看 digest 区分。digest 是不可变的,tag 是可变的。

什么是多架构镜像?

Multi-architecture Image 多架构镜像是某个镜像针对不同操作系统/系统架构的不同镜像实现。即镜像的 : 是相同的,但是针对的操作系统/系统架构不同(如 linux/amd64、linux/arm64、windows/amd64)。无论用户使用什么操作系统,通过 docker pull 拉取到的一定是针对该操作系统的镜像,用户无需考虑操作系统问题。Docker Hub 能根据 pull 请求自动选择对应的镜像。

什么是分发散列值(Distribution Hash)?

在 push 或 pull 时,都会对镜像进行 压缩 以减少网络带宽。但压缩会改变镜像内容,导致传输后与 digest 不符合。为解决,Docker 为镜像配置了 Distribution Hash(分发散列值) :在镜像压缩后计算分发散列值,随镜像一同发送;接受方收到后,立即计算压缩后镜像的分发散列值,与携带的对比,相同则传输没问题。Distribution Hash 解决了压缩传输后与原始 digest 不符的验证问题。
