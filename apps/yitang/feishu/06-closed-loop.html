第 6 章 · 跑闭环，完成一次交付

真正的完成标准不是"它回答了我"，而是"它完成了一次可验收的工作"。

🤔 为什么最后必须复测？

能跑通一次，不代表已经可用。Agent 可能读错资料、遗漏字段、误判内容，或者把结果写到了错误位置。

💡 关键区分：真正的完成标准不是"它回答了我"，而是"它完成了一次可验收的工作"。

🌡️ 先打一个体感分

验收之前，先给这次交付打一个体感分：

30 分

能跑，但结果不可用

50 分

结果勉强能用

70 分

能稳定交付

90 分

可以直接交给同事用

📊 追问一句：差的那几十分，卡在输入、流程、规则、权限、输出格式哪个环节？这就直接对应第 7 步"只改一个变量"。

⚠️ 一个反例：先跑 60 分永远对吗？

不对。涉及钱、安全、合规的低容错场景，不能 60 分就上。所以本次课程限定在"出错可人工接管"的任务 —— 第 2 章已经说死，这里再强调一次。

🧪 三类测试样例

只测一个"正常样例"很容易产生错觉。最小闭环至少要准备下面三类样例：

类型 怎么准备 期望行为
正常样例 字段齐全、格式正确、内容典型 按主流程完成并交付可用结果
边界样例 缺少一个关键字段，或出现含糊表达 明确标记"待确认"，不自行补写事实
异常样例 链接无权限、格式错误或规则冲突 停止后续处理，说明失败位置并给出恢复方式

通过标准：三类样例都符合预期，才说明 Agent 不只是"会做"，还知道什么时候不能继续做。

🔁 闭环 8 步

  1. 1.准备一个正常样例，尽量接近未来真实工作
  2. 2.保存输入资料，确保之后可以复测
  3. 3.让 Agent 执行完整任务
  4. 4.记录 Agent 的关键处理过程和判断结果
  5. 5.打开飞书中的最终输出，按成功标准人工验收，打体感分
  6. 6.记录问题：漏了什么、错了什么、哪里不稳定
  7. 7.让 Codex 只修改导致问题的那一个变量（输入不清/流程遗漏/规则不明/工具权限/输出格式，五选一）
  8. 8.用同一个样例重新运行，比较前后结果

🚀 跑通之后：定下一个里程碑：先让这个 Agent 稳定跑 10 次不出错，还是复制出第二个岗位？一次只攻一个。

📋 验收清单

  • ☑输入资料正确，Agent 没有读错对象
  • ☑主要步骤都执行了，没有跳过关键判断
  • ☑输出结构符合岗位要求
  • ☑结果已经写入正确的飞书位置
  • ☑需要人工确认的内容被明确标记
  • ☑Agent 没有对缺失事实自行猜测
  • ☑用同一个样例复测后，问题已经减少或被清楚记录

🤖 可以直接给 Codex 的提示词

请对刚才这次 Agent 运行做一次交付复盘。
请分别列出：
1. 本次输入是否正确；
2. 哪些步骤已经完成；
3. 哪些结果符合成功标准；
4. 哪些地方存在遗漏、误判或不稳定；
5. 下一版只需要修改的前三个点。

不要直接扩大任务范围，也不要把未经确认的内容写成事实。

✅ 过关标准

最低合格标准：

  • ①能看到输入
  • ②能看到 Agent 在执行
  • ③能打开最终输出
  • ④人工确认结果基本可用

更高一档：

  • ①复盘时只改了一个变量，并记录了改前改后的对比
  • ②本次修正已写进成长档案
  • ③你写下了下一个里程碑

📌 重要认知：今天只走完第一轮，真正的 Agent 是打磨 5 到 10 轮、甚至 20 到 30 轮出来的。这一轮的目标不是完美，是建立"跑 → 归因 → 改 → 复测"的习惯。

✍️ 现在轮到你

完成一次真实交付，并写下三句话：

  1. 1.这次做成了什么
  2. 2.哪里出错了
  3. 3.下一版先改什么

⚠️ 常见卡点

卡点 ①：问题太多，想全改

→ 忍住。一次只改一个变量，全改的结果就是你不知道哪个改动起了作用

卡点 ②：改完没变好

→ 归因错了。回验收清单，看是哪一项没达标，重新归因

卡点 ③：跑通了但不敢交给别人用

→ 这是好事，说明你在意边界。先自己用一周，再让一两个同事小范围试用

💎

能跑通一次，只说明"它会做"；
稳定跑十次，才说明"它能用"。
